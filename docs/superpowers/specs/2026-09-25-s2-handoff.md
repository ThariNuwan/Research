# S2 → S3b/S4 handoff: residual risks and what they cost

**Status:** written at the close of S2, 2026-09-26
**Spec:** `2026-09-25-s2-evaluation-corpus-design.md`
**Plan:** `../plans/2026-09-25-s2-evaluation-corpus.md`

S2's artifact is `eval/ground_truth/corpus-v1.json`: 26 cases (21 vendored, 5
hand-crafted), 10 contrastive pairs, 5 scenarios, all five domains, zero
orphan cases. Its six acceptance gates (`tests/test_s2_gates.py`) are green,
and each was mutation-tested to confirm it can fail. This document records
what that green suite does **not** guarantee, so S3b and S4 inherit the gaps
explicitly rather than rediscovering them. Every item below is either a live
risk or a lesson that cost something to learn while authoring the corpus.

---

## 1. Single-factor purity is an authored judgement, not a proven property

No class-to-factor mapping exists anywhere in this repository - not in
`taxonomy.json`, not in `rubric.json`, and S2 deliberately does not create
one (design spec §1: a table the evaluator writes and the scorer later
consumes would couple the grader to the graded, which
`test_eval_does_not_import_the_framework` exists to prevent). Gate 5 makes
each pair's class difference explicit, re-derivable from real adapter
output, and checks that the class-difference-to-factor relation is a
function. None of that establishes that the *named* factor is the correct
one for a given difference - only that the same difference is not claimed
twice for two different factors.

A pair can be internally consistent, mechanically clean, and still test the
wrong factor. **Cost if ignored:** a contrastive-pair pass rate that
measures something other than what the results claim it measures, with no
artifact that would reveal the mismatch on its own. The nearest available
mitigation is that the blinded reviewer (item 7) sees the pairs too, and a
disagreement there is the signal to look again - not a guarantee.

## 2. `networking-egress-exposure` maps to no rubric factor

The Public Exposure factor is inbound-only by its own closed
supported-pattern list (SG/NSG **ingress** open to 0.0.0.0/0 or ::/0,
public-IP/publicly_accessible flags, public storage, Kubernetes
LoadBalancer/NodePort/Ingress); egress appears in no level. The taxonomy
defines `networking-egress-exposure` itself as "a distinct property from
inbound exposure." An earlier draft of the corpus rested a pair on this
class anyway - a class named "exposure" was read as exposure evidence
without checking the factor's own text, the same trap named in item 1 - and
that pair was retired once the erratum surfaced (design spec §1.1).

A finding in this class scores on severity plus declared context only; the
data-exfiltration risk it represents is not captured by any of the six
factors. **Cost if ignored:** the model silently under-scores a real
class of finding while nothing in a scoring run signals that the class is
even in play. S4 must rule - widen the factor set to represent it, or state
plainly that this risk is out of scope for the current model.

## 3. `containers-host-isolation-breakout` maps to no rubric factor either

Flagged independently by both the corpus's author and the blinded reviewer
during the containers scenario's oracle review, which is stronger evidence
than either noticing alone. The class covers `hostPID`, sensitive
`hostPath` mounts and service-account-token automount - pod-spec privilege
elevation that Privilege's own wording (the Kubernetes `securityContext`
object) does not obviously reach, and the reviewer said explicitly that it
declined to credit pod-spec elevation under a narrow reading of that
wording. It maps cleanly onto none of the six factors as literally worded -
the same class of gap as item 2, on a different platform.

**Cost if ignored:** identical in shape to item 2 - a real privilege-adjacent
risk with no factor term to carry it, and a container workload that opens
this path scores no differently from one that does not, on this dimension.
S4's ruling on item 2 should cover this class in the same pass rather than
as an afterthought, since both are instances of one gap: findings whose
risk is real but whose factor is undefined.

## 4. The exposure pair's evidence is single-sourced

On `aws_s3_bucket.public_exposed`, the `storage-public-accessibility` class
is attributed by checkov's `CKV2_AWS_6` alone - a graph check resolving the
bucket-to-public-access-block relationship, and therefore the semantically
correct attribution, since the bucket is the exposed asset. tfsec's and
trivy's eight equivalent findings instead attribute the same class to the
sibling `aws_s3_bucket_public_access_block.public_exposed`, which is not a
case in this corpus (naming it would have required a case with, on its
private twin, zero findings from any scanner - disqualified per the
no-empty-side constraint discovered while authoring the privilege cases).
`aws_s3_bucket_policy.public_exposed`'s own unmapped checkov finding
(`CKV_AWS_70`) is outside any case too.

The pair stands - the attribution is right, not merely available - but it
rests on one scanner's reading rather than three. **Cost if ignored:** were
`CKV2_AWS_6` to disappear in a future checkov release, this identity would
carry no exposure class at all and the pair would collapse silently rather
than visibly. Worth a standing check whenever the checkov pin moves.

## 5. The compute scenario is contested

The blinded reviewer ordered `ec2-db-app-compute` above `ec2-web-host-compute`;
the corpus's author ordered them the other way, and the disagreement is
recorded as `partial` in the scenario's `disagreement_note`. The reviewer's
reading is the better grounded of the two: it read the Privilege factor
from source (`aws_instance.db_app` carries `iam_instance_profile` at
`db-app.tf:247`, whose `aws_iam_role_policy.ec2policy` grants `s3:*, ec2:*,
rds:*` on `Resource "*"` at `db-app.tf:206-225`, while `web_host` carries no
instance profile at all), where the author's ordering rested on finding
breadth plus one CRITICAL-severity hardcoded-secret finding - and finding
breadth is not one of the six rubric factors, while Privilege is.

The author's ordering nonetheless stands as ground truth, because the
resolution rule (design spec §5) was pre-registered before this was known
and exists precisely so a disagreement is never resolved after the fact
toward whichever answer suits the outcome. **Cost if ignored:** one of five
scenario orderings is knowingly not the best available reading of the
rubric against the evidence. Re-authoring it requires a fresh blinded
review, not a patch to the existing one - patching would mean the same
person who saw the disagreement also gets to choose how it is resolved,
which is the exact coupling the resolution rule exists to prevent.

## 6. `severity` has no contrastive pair at all

Not "not yet mined" - not pair-testable by any construction found, including
a hand-crafted attempt. Measured across corpus v0 and that attempt: zero
same-type resource pairs share an identical issue-class set while differing
in maximum severity. The reason is structural: an identical class set means
the same rules fired, and a rule's severity is fixed, so two resources
differing in severity within one class would require a *different* rule to
have fired - which changes the class set (or the resource type) too.
Checkov also contributes no integer severity at all in this corpus, which
narrows the raw material further. Gate 2 asserts the zero directly rather
than leaving it as a silent absence.

**Cost if ignored:** if a future reader "fixes" this by authoring a pair
that spans two different classes or two different resource types to force
a severity contrast, that pair does not isolate severity - it isolates
whatever else changed alongside it, and reintroduces exactly the confound
gate 2 exists to keep out. Severity's contribution to the additive model is
still fully exercised by every case's finding set; only its *contrastive
pair* is absent, and it costs little, since severity is a direct term in
the sum rather than the object of the research contribution the way the
other five factors are.

## 7. The blinded reviewer shares a model family with the authoring tooling

Both the corpus author's own reasoning tools and the blinded reviewer used
for the oracle protocol (design spec §5) draw on the same model family.
Correlated blind spots are possible - a shared training-driven habit of
reading ambiguous rubric language the same way, for instance - and cannot
be measured from inside this project: there is no independent instrument
to compare against without introducing a second blinding problem.

**Cost if ignored:** the oracle's agreement figures (item 8's headline
numbers) could overstate how well an independent human expert would agree
with the framework's ordering, without any signal inside the data that
this is happening. A supervisor review of a sample by a human domain
expert would bound this; it does not exist yet and does not block S2, but
it is worth budgeting before the agreement figures are presented as
validating anything beyond internal consistency.

## 8. Two fixture directories now exist, and they can drift apart

`tests/harvest/fixtures/` (corpus v0, five golden captures, never touched by
S2) and `tests/harvest/fixtures/authored/` (three captures over
`corpus/authored`, added by S2) are both real scanner output, captured at
different times against different roots. Nothing enforces that the pinned
scanner versions used to capture one still match the versions used to
capture the other if either is ever re-captured independently - a
`tools/bootstrap.ps1` version bump re-captured for one root but not the
other would leave two fixture sets nominally from "the pinned toolchain"
that were not actually captured by the same pinned toolchain at the same
moment.

**Cost if ignored:** gate 5's cross-pair consistency check spans both
directories in one adapter run; a drift between them would not necessarily
fail that gate (each case's own re-derivation is checked against its own
fixture set) but would mean "the corpus's adapter output" is quietly two
different things depending on which case is asked. Bounded today by never
touching v0's fixtures and by the authored fixtures being regenerable from
the committed `.tf` files at any time; not eliminated.

## 9. `expected_band` is set nowhere in corpus v1

Every `expected.findings` entry across all 26 cases omits `expected_band`
(the schema's own optional, secondary field - "ordering is the primary
signal"). This corpus tests **orderings**: contrastive-pair direction and
scenario tiers. It tests nothing about where a score lands relative to the
Critical/High/Medium/Low thresholds.

**Cost if ignored:** a scoring engine could rank every case in this corpus
in exactly the order this ground truth expects and still put every one of
them in the same priority band - the ordering-quality metrics would report
perfect performance while the band-mapping/threshold behavior (a separate
and equally real way for the framework to fail practitioners) goes
completely untested. Any sensitivity analysis over the frozen thresholds
(PLAN Q10) must be understood as analysing a mapping this corpus does not
independently validate, and must not be reported alongside the ordering
metrics as though it carried the same evidential weight.

## 10. Five of 26 cases are hand-crafted by the framework's own author

`corpus/authored/iam_privilege.tf` (three IAM policy cases) and
`corpus/authored/storage_public_exposure.tf` (two S3 bucket cases) exist
because corpus v0 cannot isolate Privilege or the second Exposure pair by
any construction found (items 1's sibling gap; design spec §1 and §1.1).
They are the minimum v0 could not express, not a general authoring
convenience, and their declared context and expected findings are drawn
from real scans of the authored root rather than asserted.

**Cost if ignored:** every hand-crafted case is a case whose "what would a
real misconfigured resource look like" judgement was made by the same
person building the framework being evaluated, on top of code the same
person wrote. This is disclosed rather than hidden, and it is bounded to
exactly the two factors v0 could not supply, but it is not eliminated by
disclosure - a hostile reading of the results should treat these five
cases' contribution to the headline pair-pass rate (3 of 10 pairs - both
privilege pairs plus the second exposure pair) as weaker evidence than the
7 pairs mined entirely from third-party vendored code.

## 11. S1's rubric citation audit is still open

`src/iacrisk/data/rubric.json` still carries `citations_audited: false`.
The blinded oracle protocol (design spec §5) deliberately withheld the
per-level `source` attribution strings from the reviewer for exactly this
reason - nothing unaudited should influence a judgement that reaches the
results - and gave it only the level *definitions*, which were frozen
before any scoring output existed and are pinned by tests independently of
the citation audit. That withholding is sound and does not need revisiting.

**Cost if ignored:** unchanged from the S1 handoff's item 1 - no dissertation
text may quote a `source` string until all 33 levels are audited against
primary sources and the audit is committed, flipping the flag. S2 adds no
new instance of this risk; it is carried forward because corpus v1's
existence does not retire it, and because it would be an easy thing for a
future session to assume was resolved simply because a second sub-project
has since shipped.

## Two numbers that must be reported as two, not as one

**Pairs: 10 authored, 10 contributing.** All ten fully contribute to the
prioritization-quality claim; none touches a case flagged
`excluded_from_quality_claims`. An earlier state of this corpus had one
excluded pair (`exposure-security-group-rule`, resting on the retired
egress class); it was retired rather than kept and disclosed, so there is
no "9 of 10" figure to report and this document does not restate one.

**Scenarios: 5 authored, 3 free of excluded cases.** The networking
scenario contains `sgr-ingress-low-exposure` (exposure `unresolved` under
the literals-only extraction rule - a real cross-resource CIDR reference,
not a defect in the case) and the compute scenario contains
`ebs-web-host-storage-compute` (sensitivity `defaulted`, exercising PLAN
Q4's missing-declared-value path on purpose). Both are correctly present in
their scenarios - the ordering around them is still meaningful - but both
findings are flagged `excluded_from_quality_claims` and any headline
scenario-level figure should state "5 authored, 3 free of excluded cases"
as two numbers, never averaged into a single "how many scenarios are
clean" claim.

## A process lesson, recorded because it cost real time twice

**A class named for a factor is not evidence of that factor.** This project
walked into the identical trap twice: `iam-authentication-controls` looked
like Privilege-scope evidence and is authentication configuration instead,
and `networking-egress-exposure` looked like Public-Exposure evidence and
is explicitly, in the taxonomy's own words, "a distinct property from
inbound exposure." Both instances were caught by re-reading a factor's or
class's own definition text rather than trusting its name, and the second
instance was caught only after a pair built on the wrong basis had already
been committed. The generalisable rule for anyone extending this corpus or
building a class-to-factor relationship in S4: match on definitions, never
on names, and re-read the definition every time, because the name is
designed to be evocative and evocative is exactly what makes it
untrustworthy as evidence.
