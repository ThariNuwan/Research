# S3b handoff — residual risks

**Sub-project:** S3b, pipeline layer 3 (context extraction), declared-context path only.
**Spec:** `docs/superpowers/specs/2026-09-30-s3b-context-extraction-design.md`
**Plan:** `docs/superpowers/plans/2026-09-30-s3b-context-extraction.md`
**Gates:** `tests/test_s3b_gates.py` — seven, all green. 748 tests in the suite.
**Read this before starting S3c or S4.**

Every figure below was measured on this host against the committed fixtures and the
vendored corpus. Each item says what it costs if ignored, because an unranked list of
caveats is not a handoff.

---

## 1. Two resolution-rate numbers, and they must never be conflated

This is the most important item in this document. Spec §1.1 makes the resolution rate the
condition under which the framework ranks at all rather than a metric reported afterwards:
the five context defaults sum to 16, so an all-defaulted finding scores 17–21 — always High
— and a Checkov finding with nothing resolved lands on exactly 20.

**On the primary declared-context path** — the 209 findings whose resource `corpus-v1.json`
actually declares context for:

| Factors defaulted or unresolved | Findings | Share |
|---|---|---|
| 0 | 24 | 11.5% |
| 1 | 41 | 19.6% |
| 2 | 102 | 48.8% |
| 3 | 42 | 20.1% |
| 4 | 0 | — |
| 5 | 0 | — |

**Low-confidence (≥ 3): 42 of 209, 20.1%.** So **79.9% of findings on declared resources
sit below the frozen threshold and are usable for prioritization-quality claims.** The
framework can rank.

**Across all 1,055 corpus-v0 findings, low-confidence is 803 of 1,025 eligible (78.3%).**

**Cost if ignored:** reporting the second figure as the framework's resolution rate would
understate it by a factor of four and would be wrong in exactly the way reporting Tier-2's
91 same-scanner candidates as cross-scanner overlap would be. Corpus v0 is the
*measurement* corpus that produced the rule inventory; `corpus-v1` is the evaluation
corpus, and it declares only **20 identities**. Most v0 findings are on resources nobody
declared context for, so their two declared factors default by construction rather than by
any failure of layer 3.

## 2. Exposure is unresolved on 93.6% of eligible findings, by design

Per-factor unresolved counts over all 1,025 eligible findings, with declared context
supplied: **exposure 959, encryption 562, privilege 319**.

Exposure's rate is a direct consequence of PLAN Q9's closed supported-pattern list. A
resource that is not a security group or rule, not carrying a public flag, not an S3 bucket
with an attached public-access-block, and not a Kubernetes `Service` or `Ingress` resolves
`unresolved`, never low. Most corpus resources — databases, IAM objects, log groups,
parameter groups — are none of those.

**The consequence is real and belongs in the write-up.** On those findings exposure
contributes a constant 3 and does **no ranking work whatsoever**. It resolves correctly on
the cases the oracle actually turns on, which is why the networking scenario's three tiers
reproduce exactly from code — but a reader told "the framework scores exposure 0–5" would
reasonably infer the factor discriminates across the corpus, and it does not.

**Cost if ignored:** presenting exposure as a working discriminator across the corpus when
it is near-constant on nine findings in ten. The honest framing is that exposure
discriminates *within the supported patterns* and is explicitly unresolved outside them,
with the per-factor rate reported alongside any exposure claim.

## 3. Kubernetes body coverage is 46.3%; Terraform is 99.1%

The asymmetry is the story, and both halves were measured.

**Terraform: 446 findings, 442 matched (99.1%).** The four misses are all
`aws_iam_policy_document.policy`, which is a `data` block — `build_index` walks only
`document["resource"]`, so data sources are not indexed. **Zero findings carry an instance
key and the corpus contains zero `module` blocks**, so `build_index`'s flat `type.name`
keying is adequate here. That is a property of this corpus, not of the method:
`identity.terraform_identity` accepts `module_path` and `instance_key` and `build_index`
passes neither, so a corpus using modules or `for_each` would mis-key silently. **Latent,
not live.**

**Kubernetes: 579 findings, 268 matched (46.3%)**, after the container fallback in item 4
recovered 71. The dominant remaining cause is measured: of 22 YAML files under the
Kubernetes scan root, **4 fail to parse** — `deployment.yaml`, `ingress.yaml`,
`service.yaml` and `test-connection.yaml`, all Helm chart templates carrying Go templating,
which is not valid YAML. Their workloads have no body at all, so every finding on them
resolves all three parsed factors unresolved.

**Cost if ignored:** attributing the Kubernetes unresolved rate to the closed pattern list
when roughly half of it is a *parsing* gap with a known fix. Rendering Helm charts before
indexing would recover most of it and is recorded as future work, not attempted here.

## 4. A §G3 defect found by measurement, and what it implies about the others

`kubernetes.py`'s docstring claimed a container finding "resolves its exposure and
privilege from the enclosing workload's body, which this index already holds under the
workload's own identity." No lookup stripped the `[container=…]` suffix, so **0 of 217
container-scoped identities matched** — the docstring described behaviour the code did not
have. Fixed in `34747a7` with `lookup()`, which tries the exact identity then falls back to
the workload; 71 findings recovered.

**What it implies:** this defect was invisible to the whole suite. Seven gates, 746 tests,
`ruff` and `mypy` clean, and nothing failed — because every Kubernetes test supplied its own
hand-built index keyed the way the code expected. **A test that builds its own fixture
cannot discover that the real key shape differs.** The gates that caught it were not tests
at all but a measurement run over the real corpus.

**Cost if ignored:** the remaining extractors are tested the same way, so the same class of
defect could be present anywhere the real identity shape differs from a hand-built
fixture's. Before S4 reports any figure, run the extractor over the real corpus and check
the *match rate*, not just the test suite.

## 5. Decision 12 makes every `aws_iam_role` unresolved

A statement carrying a `Principal` and no `Resource` is a trust policy, not a permission
grant (measured: `aws_iam_role.ec2role`'s `assume_role_policy` is `Action = "sts:AssumeRole"`
with `Principal = {Service: ec2.amazonaws.com}` and no `Resource`). Scoring it on the
permission ladder reads the grant backwards — `sts:AssumeRole` would land at 4 as an
escalation enabler when it is the role's own trust boundary.

So a role whose only readable policy is its trust policy is `unresolved`, scoring the
conservative 4. That is correct — its real permissions live in separate attached policy
resources a bounded per-finding read does not aggregate — but it means **every IAM role in
the corpus contributes privilege 4 without evidence**.

**Cost if ignored:** treating privilege 4 on a role as a measured finding rather than a
conservative default. Aggregating role → attachment → policy is a bounded three-hop lookup
that would resolve it, and is out of scope for S3b.

## 6. Bucket publicness uses a textual principal check, not a parse

`exposure._has_public_principal` tests `'"*"' in text and "Principal" in text and "Allow"
in text` against the raw policy source rather than parsing the document. It is deliberate —
the policy arrives as a `jsonencode` expression and a public principal is a textual
property of it — but it is **not equivalent to a parse**. A policy containing
`Action = "*"` with a narrowly-scoped `Principal` would satisfy all three substrings.

No such policy exists in this corpus, so the check is correct on every case here.

**Cost if ignored:** a bucket scoring 5 — the top of the exposure ladder, the level that
asserts world-readable content — on a policy that is not public. `privilege.py` already has
`parse_policy_document`, which would give an exact answer; reusing it here is a small,
contained improvement.

## 7. Gate 6 asserts no resolution threshold, deliberately

It checks the coverage report is well-formed and internally consistent — the distribution
sums to the eligible count, the low-confidence population is exactly the tail at or above
3, all 28 taxonomy classes appear — and asserts **no minimum resolution rate**. The measured
rate is a finding to report, not a target to pass, and pinning one would convert an
empirical result into a test that must be kept green.

**Cost if ignored:** a future change that collapses the resolution rate would fail no test.
Item 1's figures are the baseline; re-measure them after any extractor change and compare,
because the suite will not do it for you.

---

## 8. Two Kubernetes parsers now exist and can drift

S3a's `resources.ResourceIndex` resolves identity from a file and line and carries no spec.
`context/kubernetes.py` reads bodies and carries no line spans. Both key on
`identity.kubernetes_identity`, which is what keeps them consistent — but nothing asserts
they see the same set of documents, and they use different YAML entry points
(`yaml.compose_all` on nodes versus `yaml.safe_load_all`).

**Cost if ignored:** a manifest one parser accepts and the other rejects produces a finding
with a resolved identity and no body, which is indistinguishable in the output from a
resource genuinely outside the pattern list. The four Helm templates in item 3 may already
be exactly this case; it was not separated.

---

## 9. `publicly_accessible` absent resolves unresolved, which may be over-conservative

Unlike EBS encryption — where AWS's effective default depends on an account-level setting
invisible in source, making `unresolved` the only honest answer — Terraform's documented
default for `publicly_accessible` is `false` and does not depend on account state. An
absent flag could therefore legitimately resolve low on that axis.

It resolves `unresolved` instead, scoring 3, because the resource may still be reachable
through a security group the bounded read did not attribute to it.

**Cost if ignored:** a defensible choice presented as a necessary one. It is a judgement
about what "exposure" means for a database with no public flag, and it contributes to
item 2's 93.6%. Worth stating as a choice in the write-up rather than leaving a reader to
assume the extractor could not read the attribute.

## 10. Deferred, unchanged

**To S3c:** the convention-based auto-inference mode for sensitivity and criticality, its
tag and naming conventions, and the auto-inference agreement metric.

**To S4:** all scoring, banding and reporting; enforcement of the coherence rules at score
time; and the ruling on the **three taxonomy classes that map to no rubric factor**, for
which §8.4's per-class factor-coverage report now supplies the counts.

**Still named future work, not attempted in S3b:** cross-scanner attribute normalization
(S3a §13), a measured `raw_records_seen` to replace S3a's derived `findings_in`, Helm
rendering before Kubernetes indexing (item 3), and the role → attachment → policy
aggregation in item 5.
