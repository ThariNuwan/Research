# S3a → S3b handoff: residual risks and what they cost

**Status:** written at the close of S3a, 2026-09-24
**Spec:** `2026-09-22-s3a-detection-normalization-design.md`
**Plan:** `../plans/2026-09-22-s3a-detection-normalization.md`

S3a's six acceptance gates (spec §10) are green and pinned as tests
(`tests/test_s3a_gates.py`). This document records what that does **not**
guarantee, so S3b inherits the gaps explicitly rather than rediscovering them
task by task. Every item below is either a live risk or a lesson that cost
something to learn on this branch, following the shape
`2026-09-19-s1-handoff.md` set for S1's own handoff.

---

## 1. `findings_in` is derived, not measured

`ScannerCoverage.findings_in` (`src/iacrisk/report.py`) is computed as
`findings_out + len(dropped)` - `AdapterResult` carries no fourth, independent
count to derive it from. A test that only checks `findings_in == findings_out
+ len(dropped)` is therefore `a == a` and cannot fail for any input;
`tests/test_report.py` names this honestly rather than hiding it, and the
retention tests close the real gap by counting raw records from the fixture
JSON independently of every adapter. But the *field itself* stays derived, so
a future adapter change that silently drops a finding (never adds it to
`findings`, never records it in `dropped`) changes nothing `findings_in`
itself would catch - only the independent-count tests would, and only for
runs they cover. **Cost if ignored:** a silent-loss regression in an adapter
could ship undetected outside the test suite, because the production code
path has no internal check of its own. Plumbing a real `raw_records_seen`
count through each adapter and into `AdapterResult` is recorded future work
for S3b or S5, not attempted here.

## 2. `normalize_severity` returns `int | str`

`rubric.normalize_severity` (`src/iacrisk/rubric.py`) returns an `int` level
or the literal string `"unknown"` - the explicit unresolved-severity state,
carried by 489 of 1055 findings in corpus v0. Every one of S3a's three
adapters already branches on it correctly (`severity_level: int | str` on
`NormalizedFinding`, never coerced). The risk is downstream, not here: any new
call site that reads `finding.severity_level` and does arithmetic on it
without checking for the string first will either raise (`int + str`) or,
worse, silently succeed by accident on the branches that already are
`int` while failing only on Checkov's 489. **Cost if ignored:** a scoring
computation that works in every manual test drawn from Trivy or tfsec rows and
breaks only when it meets a Checkov row - the 46.4% of the corpus most likely
to be under-tested precisely because it is the awkward case.

## 3. Trivy supplies no violation fingerprint, ever

By design (spec §6), `TrivyAdapter` sets `fingerprint=None` unconditionally.
The measured reason (spec §12.2) is not that trivy's `Resolution` field is
unusable - 55.7% of it carries a cleanly extractable attribute token - but
that the extracted vocabulary shares zero exact spellings with checkov's
`evaluated_keys` (18 distinct trivy tokens, 23 distinct checkov keys, 0
overlap measured). Extracting it today would add a field that never matches
anything and produce no additional Tier-1 collapse. The consequence: every
pair of trivy findings sharing identity and issue-class lands in Tier 2 as a
same-scanner candidate and can never be separated by this pipeline - 71 of
corpus v0's 91 same-scanner candidates are trivy, for exactly this structural
reason (`src/iacrisk/dedupe.py`'s module docstring has the full count). **Cost
if ignored:** reading trivy's same-scanner candidate rate as evidence of poor
precision in trivy's own rule granularity, when it is actually a property of
this pipeline's fingerprint extraction not covering trivy at all. The fix -
cross-scanner attribute normalization - is named future work (spec §13), not
attempted in S3a, S3b, S4 or S5 as currently scoped.

## 4. `_unresolved_cause` cannot see which resolution branch actually ran

`report.py::_unresolved_cause` classifies an unresolved Kubernetes finding
from `(file_path, line_range, unparseable)` alone. Its `LINE_UNMATCHED` bucket
therefore also absorbs a fourth, distinct state its own docstring names but
`NormalizedFinding` has no field to record: "no resource index was supplied
at all" (`index is None`), as opposed to "a line was supplied and looked up
but matched no span." Unreachable today - no caller in corpus v0 ever invokes
a Kubernetes adapter run with `index=None` - but the adapter itself does not
record which of its three branches (`by_address` hit, `by_line` hit, neither)
produced `<unresolved>`, only that one of them did. **Cost if ignored:** if a
future caller ever does omit the index on a real Kubernetes run, every one of
those findings is silently folded into `LINE_UNMATCHED`'s zero-population
bucket rather than surfaced as its own cause, understating a configuration
mistake as a data-quality one.

## 5. `build_invocations` resolves against a fixed module-level `REPO_ROOT`

`src/iacrisk/scanners/invoke.py::build_invocations` calls
`_resolve_exe(scanner, REPO_ROOT)` with the module-level constant baked in,
not a parameter - unlike `_resolve_exe` itself, which does take an injectable
`repo_root` for exactly this reason. The integration tests that exercise
`build_invocations` end-to-end therefore skip on any checkout without a
bootstrapped, gitignored `tools/resolved.json`. **Cost if ignored:** a CI
environment, or any fresh clone that has not run `.\tools\bootstrap.ps1`,
loses that integration coverage with no louder signal than a smaller "passed"
count in the summary line - exactly the kind of quiet gap the pytest-exit-code
trap below also produces, and just as easy to miss in the same glance at a
transcript.

## 6. `run()`'s 900-second timeout is a re-derived literal

`SCANNER_TIMEOUT_SECONDS = 900` in `invoke.py` is deliberately not imported
from `tools/harvest/run.py`'s own constant of the same name and value - harvest
isolation (`tests/test_architecture.py`) forbids the import, so the module
docstring states plainly that the two are "meant to stay in step" by
convention, not by the type checker. **Cost if ignored:** a future change to
harvest's timeout (raised for a slower CI runner, say) silently stops applying
to S3a's own invocation path, and nothing fails loudly to announce the drift -
the two numbers simply diverge until someone happens to compare them.

## 7. Two tasks on this branch shipped a fix round without a confirmed red state

Task 9 (the retention report) and Task 10 (lockfile-driven invocation) each
shipped at least one fix round that was not preceded by a verified failing
test - both defects were caught instead by the controller's mutation testing,
and in one case (`report.py`'s `findings_in` consistency test, item 1 above)
the test as originally shaped genuinely could not fail for the property it
claimed to check. Task 11 closes with explicit red/green mutation evidence for
all six gates specifically because of this precedent. **Cost if ignored:** a
green suite proves the code currently passes its own tests; it does not prove
those tests could ever have failed. Skipping the red-state check is how a
tautological test ships looking exactly like a real one.

## 8. The rubric's citation text is still unaudited

Carried forward unchanged from the S1 handoff (`2026-09-19-s1-handoff.md`
item 1), because nothing in S3a touches it: `src/iacrisk/data/rubric.json`
still asserts `citations_audited: false`, separately from
`structure_frozen: true`. The anchor test only checks that a standard's name
(`CVSS`, `NIST`, `NSA`, `OWASP`, `FIPS`) appears in each level's `source`
string - it is structurally blind to a wrong appendix, an inverted metric, or
a misquote. **Cost if ignored:** quoting an unaudited `source` string in the
dissertation as though it were verified. No `source` string may be quoted
until an audit of all 33 levels against their primary sources is committed and
the flag is flipped.

---

**For S3b specifically:** items 1 and 2 are the two most directly load-bearing
for a scoring engine built on top of this record - a scoring computation is
exactly the kind of call site item 1's silent-loss gap and item 2's
`int | str` branch both threaten silently. Read both before writing the first
line of scoring code.
