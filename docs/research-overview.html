Risk-Aware Prioritization for Cloud IaC Misconfigurations

A framework that re-ranks the findings existing scanners already produce — using cloud context — so teams remediate what actually matters first.

Jayathissa E.A.T.N. (258243J) · MSc in Computer Science (Cloud Computing) · University of Moratuwa

Design locked Externally reviewed — approved at round 4 of 5 Implementation: next phase
01

The problem

Checkov, tfsec and Trivy detect misconfigurations well. What they emit is a flat list of severity labels with no awareness of where a resource sits, what it holds, or who can reach it.

Alert overload

A publicly-exposed production database holding customer data is presented alongside a cosmetic tagging violation in a sandbox. Both say “HIGH”.

Severities are not comparable

Each scanner assigns severity by its own convention, so a combined list cannot be ranked meaningfully without normalization.

Duplicate reporting

The same underlying problem is often flagged by several scanners at once, inflating the apparent alert count.

Missing context

Internet reachability, IAM blast radius, data sensitivity, environment criticality and encryption state determine real business risk — and none of it is in the finding.

02

The framework — a five-layer pipeline

Detection is delegated to the scanners. The contribution is layers 3–5: context, scoring, and ranked reporting.

LAYER 1

IaC Input

Terraform (HCL) and Kubernetes YAML manifests.

LAYER 2

Security Scanning

Checkov, tfsec, Trivy as subprocesses (pinned) → one normalized finding record.

LAYER 3

Context Extraction

Five contextual attributes attached — two declared, three parsed from code.

LAYER 4

Risk Scoring

Explainable weighted-additive model. Not machine learning.

LAYER 5

Reporting

Ranked, banded remediation list — JSON plus a human report.

Independent evaluation harness

Consumes the JSON output separately, so the framework never grades its own results.

03

The scoring model

Five contextual attributes plus scanner severity make six scoring factors. Every factor is inspectable and adjustable, and each score decomposes into named contributions — so a reviewer can always see why a finding ranked where it did.

Risk Score = Severity 1–5 + Exposure 0–5 + Privilege 0–5 + Sensitivity 0–5 + Criticality 0–5 + Encryption risk 0–3

Range 1–28. Sensitivity and criticality are declared (not reliably derivable from IaC code); the rest are parsed from the scanner output and the resource definition.

Priority bands

Bands are defined by remediation semantics first, then mapped onto score intervals — fixed a priori and frozen before evaluation, never tuned to fit the test data.

How a score is built — a contrastive pair

Two configurations identical in every respect but one factor. This is the mechanism the evaluation uses to prove a contextual factor causes a rank change — here, turning off encryption moves the finding across a band boundary.

05

How it will be evaluated

Evaluated on prioritization quality, not detection accuracy — detection is delegated to the scanners. Framed as controlled artifact validation, not generalizable empirical proof.

Normalization / retention coverage

What fraction of scanner findings the pipeline correctly normalizes and carries through.

Prioritization usefulness

Measured against a pre-registered oracle: contrastive-pair pass/fail plus independently-reviewed scenario orderings.

Alert reduction

Two separate numbers, never combined — reduction from deduplication, and reduction in the Critical/High band.

Ranking consistency

Two separate measures — auto-inference agreement (heuristic quality) and model sensitivity under threshold/weight perturbation.

Baseline comparison

Rank-change table against a severity-normalized baseline, each change justified by named factors.

Corpus

~20–30 controlled cases across storage, networking, IAM, compute and containers — TerraGoat/KubeGoat plus hand-crafted contrastive pairs.

Guarding against circularity.

Weights and thresholds are fixed a priori and frozen before evaluation; movement is reported as a sensitivity analysis, never as tuning. Oracle labels are pre-registered before any scoring output exists and independently reviewed, so the rubric author does not also set the answer key.

07

What happens next

Five specification artifacts come before any code — every downstream component depends on them. Each carries an acceptance gate so a weak artifact cannot pass silently.

  1. Issue-class taxonomy + scanner-rule-ID mapping table. Gate: every rule ID emitted across the corpus maps to an issue-class or an explicit unmapped entry; all five categories covered.
  2. Per-factor scoring rubric config (source-anchored to CVSS, NIST SP 800-30, NSA-CISA, OWASP). Gate: every score point cites a source; each factor declares its unresolved-handling policy.
  3. Scanner severity-normalization table. Gate: every native severity level mapped to the common 1–5 scale with a written justification.
  4. Evaluation ground-truth schema. Gate: validates on all corpus cases; the harness rejects ill-formed expected outputs rather than skipping them.
  5. Canonical-identity specification (Terraform + Kubernetes). Gate: defined for every resource shape in the corpus — modules, for_each/count, namespace/kind.

Then: implement the five-layer pipeline → build the independent evaluation harness → run the corpus → report the five metrics and the sensitivity analysis.
